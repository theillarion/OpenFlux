# OpenFlux в Docker (docker compose)

Полное описание настроек Docker-запуска OpenFlux: ролей, переменных окружения
и типичных проблем. Об архитектуре клиента и exit-ноды см. [README.ru.md](README.ru.md).

Один образ собирается в двух ролях, выбираемых через compose-профили:

| Роль | Профиль | Где запускать | Привилегии |
|------|---------|---------------|------------|
| **client** | `--profile client` | локально (твоя машина) | не нужны |
| **exit-node** | `--profile exit-node` | Linux VPS | `NET_RAW` + `NET_ADMIN` (compose выдаёт сам) |

Две половины напрямую не общаются: они встречаются внутри сервиса-посредника
(Яндекс.Документ, звонок MAX и т.п.). Поэтому настраивать нужно оба конца
одинаково — см. [Совместимость концов](#совместимость-концов).

## Быстрый старт

```bash
cp .env.example .env    # заполнить переменные (см. таблицу ниже)
```

Клиент — SOCKS5-прокси на `127.0.0.1:1080` хоста:

```bash
docker compose --profile client up -d --build
```

Exit-нода — на VPS:

```bash
docker compose --profile exit-node up -d --build
```

Логи: `docker compose --profile <профиль> logs -f`.
Остановка: `docker compose --profile <профиль> down`.

## Переменные окружения

Задаются в `.env` (в корне, рядом с `docker-compose.yml`) или инлайн перед
командой: `DOC_URL=... docker compose --profile client up -d`.

| Переменная | Роль | По умолчанию | Описание |
|------------|------|--------------|----------|
| `TRANSPORT` | обе | `yandex` | Канал-посредник: `yandex`, `vyandex`, `oneme`, `cupsonline`, `mailru` |
| `DOC_URL` | обе | — | Ссылка на общий документ/канал (для `yandex`/`vyandex`/`mailru`; для `cupsonline` — список комнат) |
| `MAX_TOKEN` | обе | — | Web-токен MAX (только для `oneme`) |
| `MAX_UID` | обе | — | ID **другой** стороны в MAX (только для `oneme`) |
| `SOCKS5_LISTEN` | клиент | `:1080` | Адрес SOCKS5 **внутри** контейнера (менять незачем) |
| `SOCKS5_PORT` | клиент | `1080` | Порт **на хосте**; поменять, если 1080 занят |
| `MODE` | exit-node | `l4` | Бэкенд exit-ноды: `l4` или `l3` (см. ниже) |
| `CODEC` | обе | `batched` | Кодек: `batched` (zstd) или `legacy` (старый LZ4) |
| `ENCRYPTION_KEY` | обе | — (без шифрования) | Общий секрет AES-256-GCM, минимум 16 символов |
| `EXIT_LOCAL_IP` | exit-node | авто | Фиксация egress-IP для `MODE=l3`; внутри контейнера обычно не нужна |
| `DEBUG` | обе | `0` | `1` — подробный per-packet лог (шумный) |

## Каналы-посредники (TRANSPORT)

- **`yandex`** — Яндекс.Документы (старый редактор, WebSocket). Создайте документ,
  включите доступ по ссылке и укажите ссылку в `DOC_URL` у обоих концов.
- **`vyandex`** — Яндекс.Документы 2.0 / Volga (HTTP relay + WebSocket). Настройка та же.
- **`mailru`** — Облако Mail.ru (WebSocket). Принимает короткий weblink
  (`AbCdEfGh1/IjKlMnOp2`) или полную ссылку (`https://cloud.mail.ru/public/...`).
- **`oneme`** — мессенджер MAX (WebRTC DataChannel). Каждая сторона использует
  свой Web-токен (`MAX_TOKEN`) и указывает ID другой стороны (`MAX_UID`):
  клиент дозванивается до exit-ноды, поэтому клиенту нужен uid exit-ноды,
  а exit-ноде — uid клиента.
- **`cupsonline`** — Cups.online (Centrifugo-комнаты). Exit-нода при старте
  печатает в лог base64-список комнат; этот список нужно передать клиенту
  в `DOC_URL`:
  ```bash
  docker compose --profile exit-node logs exit-node | grep -i room
  ```

## Режимы exit-ноды (MODE)

| `MODE` | Как работает | Требования | Скорость |
|--------|--------------|------------|----------|
| `l4` (по умолчанию) | TCP терминируется в userspace-стеке gVisor, затем пересоздаётся до реального сервера | никаких | ниже (двойное терминирование) |
| `l3` | Сырая пересылка IP-пакетов (SNAT/DNAT + conntrack), одно сквозное соединение | Linux, `NET_RAW`/`NET_ADMIN` (compose уже выдаёт) | выше |

Начинайте с `l4` — он работает всегда. Правило iptables против kernel-RST
entrypoint ставит сам, внутри netns контейнера: на хост оно не влияет и его
не нужно добавлять вручную.

## Шифрование (ENCRYPTION_KEY)

Без ключа содержимое туннеля внутри канала не зашифровано (посредник
теоретически видит трафик). С ключом канал заворачивается в AES-256-GCM.

- Минимум 16 символов, иначе бинарник не стартует.
- Значение должно быть **одинаковым** на клиенте и exit-ноде.
- Передаётся как переменная окружения и материализуется во временный файл
  внутри контейнера — тома монтировать не нужно.

## Совместимость концов

Клиент и exit-нода соединятся только если у них совпадает:

- `TRANSPORT`;
- `DOC_URL` (или пара `MAX_TOKEN`/`MAX_UID` для `oneme`, с учётом того,
  чей uid куда подставляется);
- `CODEC` — форматы `batched` и `legacy` несовместимы по сети;
- `ENCRYPTION_KEY` (если используется).

## Безопасность

- SOCKS5-сервер клиента **без аутентификации** — compose публикует его
  только на `127.0.0.1`. Не публикуйте порт на `0.0.0.0`; для доступа с других
  устройств используйте SSH-туннель (`ssh -L 1080:127.0.0.1:1080 vps`).
- Exit-ноде нужны `NET_RAW`/`NET_ADMIN`, они ограничены netns контейнера.

## Типичные проблемы

| Симптом | Причина и решение |
|---------|-------------------|
| `bind: address already in use` при старте клиента | Порт 1080 на хосте занят — задайте `SOCKS5_PORT=<другой>` |
| `encryption secret must contain at least 16 characters` | Ключ короче 16 символов — удлините `ENCRYPTION_KEY` |
| Соединение «поднимается», но данных нет | Не совпадает `CODEC` или `ENCRYPTION_KEY` между концами |
| `WARNING: iptables failed (missing NET_ADMIN?)` | Контейнер запущен без `--profile exit-node` (нет капов); правило не установлено, соединения будет рвать ядро |
| Exit-нода стартует, клиент не находит канал | Проверьте, что `DOC_URL` одинаковый и документ доступен по ссылке из браузера |
| `cupsonline`: клиент не знает, куда подключаться | Скопируйте base64-список комнат из логов exit-ноды в `DOC_URL` клиента |
